# Contributing to Genomewalk

For a static preview, run `docker compose up --build`. For development with hot
reload, use Node.js 24 LTS. Install with `npm ci`, start with `npm run dev`, and run
`npm run check` before submitting a change. `npm run format` formats maintained
source and documentation. `src/routeTree.gen.ts` is generated by TanStack; edit
the route files instead. Keep the generated route tree versioned so a fresh
checkout can run type checking before its first Vite build.

`package.json` declares Node.js 24 or later in `engines.node`. npm warns about an
unsupported version during dependency installation; it does not switch Node
versions. Docker selects Node.js 24 independently.

Commit source, tests, documentation, `package-lock.json`, the public catalogues
in `public/ref/`, and the documented HG002 teaching sample. Keep local work in
`tmp/` and generated document exports in `output/`; both are ignored, along with
builds, coverage reports, input caches and credentials. Ignore rules do not remove
files that Git already tracks. Do not add personal genomes to the public folders.

The small root configuration files are also source and belong in Git:

| File                             | Purpose                                                                      |
| -------------------------------- | ---------------------------------------------------------------------------- |
| `.gitattributes`                 | Uses consistent text line endings and preserves compressed assets as binary. |
| `.gitignore`                     | Keeps local data, credentials, caches and generated output out of commits.   |
| `.prettierrc`, `.prettierignore` | Share formatting rules and identify files the formatter should leave alone.  |

`package-lock.json` is the dependency lockfile used by `npm ci` locally and in CI.
Public reference files are a deliberate exception to ignoring generated output:
the static deployment includes them without running the offline pipelines.

Start with [ARCHITECTURE.md](docs/ARCHITECTURE.md). Write new code in `.ts` or
`.tsx`; scripts and tests run directly on Node 24. Use explicit relative file
extensions and type-only imports for contracts. `npm run typecheck` checks the
browser, tools and tests separately. Component-specific CSS Modules belong next
to their components; shared lesson styles and design tokens belong in `src/styles/`.
The linter uses Node's native TypeScript config support through the package script. Keep parsing, matching and
statistics independent of DOM rendering. Add regression tests for changed data
behavior using Node's built-in test runner. Include fixtures that demonstrate
missing, malformed or contradictory data when touching a reader. Avoid tests
that only repeat the implementation.

For a UI change, check a wide screen and a narrow screen, keyboard navigation,
and reduced-motion behavior. For importer changes, use the
[synthetic fixtures](docs/CONSUMER_FILES.md#synthetic-fixtures), run the applicable chapters in a different order, visit
Your results directly, navigate back, and change files. Also exercise the public
HG002 VCF path. A test file with no catalogue match must not produce a negative
health conclusion.

The supported release checklist is in [VALIDATION.md](docs/VALIDATION.md).
`npm run test:data` checks the offline builders with synthetic inputs;
`npm run data:check` validates the existing public indexes.
Reference-data rebuilds (`npm run data:build`) are separate, slow network jobs; they are not required
for an ordinary UI or reader edit. Their inputs, scripts and provenance are
explained in [scripts/README.md](scripts/README.md).

Keep personal DNA files, results, filenames and credentials out of commits,
issues, screenshots and logs. Use synthetic data to describe a bug. Preserve
exact source links and provenance when changing an evidence interpretation.
Formatting or moving a scientific statement does not validate it.

The project uses the MIT license. Contributions should use compatible licensing;
third-party data and dependencies retain their own terms.

VCF processing lives in focused modules, with one lesson per file. Keep changes
within the relevant experience unless they belong to neutral infrastructure or
shared diagrams. Run `npm run test:vcf` or `npm run test:consumer` while iterating,
then the full `npm run check:release` before release. CI runs that release check inside Docker
on pushes to `main` and pull requests.

The [regression snapshot guide](docs/VALIDATION.md#regression-snapshots) explains
the reviewed fixtures in `tests/fixtures/` and how to update intentional changes.

## Commit messages

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):
`type: short description`. Keep the subject around 50 characters and describe
one change. Use `feat:`, `fix:`, `refactor:`, `build:`, `ci:`, `docs:` or `test:`.
For example: `feat: add Docker builds` or `fix: preserve catalogue byte ranges`.
Add a body only when the reason or tradeoff needs explanation.
